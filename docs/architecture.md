## 0. 结论先行

1. **最适合 Crystal 的路线是「自绘 retained 树 + 声明式响应式」**：Gio 的事件驱动与后端抽象 + Fyne 的 retained 树与脏重绘 + Clay 的独立两遍布局内核。不选 Gio 的纯 immediate mode，不选 WebView，不选原生控件绑定。
2. **决定性依据是 2026-07 官方 Execution Contexts**：`Fiber::ExecutionContext::Isolated` 让单个 fiber 独占系统线程，官方博客点名 GUI/game loop 是其目标场景。历史上“Crystal fiber 调度与 C GUI 主线程要求冲突”这个最大障碍已被语言层面解决。本方案把 UI 主循环放在 Isolated context，其余业务留在默认 context。
3. **Crystal 的 GC 决定了不能照搬 immediate mode**：每帧重建整棵 UI 会产生大量堆对象，Boehm GC 的停等会直接变成掉帧。retained 树让对象长期存活、按脏重绘，把每帧分配压到接近零，这比 Go/Zig 更需要 retained。
4. **struct + 宏 + 编译期类型是 Crystal 的独特杠杆**：几何/颜色/布局约束用 struct 栈分配；布局算法做成可独立测试的纯函数内核；DSL 用宏在编译期展开，不付出 Ruby 式运行时动态分派代价。
5. **不重复造 GTK 绑定**：GTK4.cr 已覆盖原生控件路线，再做一个绑定没有差异化价值。本方案的差异化是“Crystal 表达力 + 可控渲染 + 单二进制分发”。
6. **这是框架设计文档，不是产品承诺**。文本 shaping、IME、无障碍是最大工作量与风险项，M2 之前必须完成技术验证，否则整个方案不成立。

## 1. Crystal 语言画像

### 1.1 与 UI 架构直接相关的能力

| 能力 | 事实 | 对 UI 架构的含义 |
|---|---|---|
| 类型系统 | 静态类型、类型推导、union 类型、nil 安全检查 | 布局约束、样式、事件可用精确类型表达，非法状态不可表示 |
| 值类型 | `struct` 继承 `Value`，栈分配、按值传递；官方性能指南建议热路径用 struct | Rect/Point/Color/Insets/约束用 struct，布局阶段零堆分配 |
| 泛型与宏 | 编译期泛型实例化、宏展开、`forall` | DSL 在编译期生成代码；渲染后端泛型化，无虚调用 |
| 方法分派 | 编译期静态分派，重载按类型解析 | 与 Rust trait 单态化等价的热路径优化手段 |
| 并发 | Fiber + Channel；2026-07 起 Execution Contexts（Concurrent / Parallel / Isolated） | Isolated 解决 GUI 主线程归属；Channel 做跨 context 事件传递 |
| 内存 | Boehm-Demers-Weiser GC，非移动式 | C 互操作安全（指针不会被移动）；但停等要求压低每帧分配 |
| FFI | `lib`/`fun` 声明式绑定 C，无需写 C 代码，`out`/`to_unsafe` 辅助 | 直接绑 Metal/Vulkan/OpenGL/FreeType/HarfBuzz，绑定层极薄 |
| 分发 | LLVM 后端，静态链接为主，单二进制 | 与 Go/Zig 同级的部署体验，优于需要运行时的方案 |
| 元编程 | 编译期可执行宏，可读类型信息 | 样式表、图标、资源可在编译期内嵌与校验 |

### 1.2 约束（必须正面处理，不能回避）

- **GC 停等**：没有分代/增量保证的官方承诺可作为帧预算依据。方案必须把“稳态帧零分配”设为硬指标，而不是依赖 GC 调参。
- **生态规模**：没有现成的 Skia/Pathfinder 级 2D 渲染器，没有成熟文本栈绑定。工作量主要在这里，不在 widget 层。
- **编译速度**：宏与泛型的大量使用会拉长编译时间，需要控制 DSL 展开规模，避免全程序单态化爆炸。
- **fiber 可跨线程迁移**：Parallel context 下 fiber 会换线程，依赖线程亲和的 C 调用（GL context、Cocoa 主线程）必须锁在 Isolated context 内，不能散落在业务代码里。
- **Windows 支持仍年轻**：平台层优先级按 macOS → Linux → Windows 排，不承诺同步交付。

## 2. 六条路线对 Crystal 的适配性判定

| 路线 | 代表 | 对 Crystal 适配度 | 判定理由 |
|---|---|---|---|
| GPU 自绘 + immediate | Gio、DVUI | **部分采纳** | 事件驱动、后端抽象、命令流值得学；纯 immediate 的每帧全量重建与 GC 冲突，不采纳 |
| GPU 自绘 + retained | Fyne | **主路线** | retained 树天然压低分配，dirty 重绘与 GC 友好；Crystal 表达力可补足 Fyne API 的冗长 |
| WebView + 原生后端 | Wails v3 | **不采纳** | 性能与无障碍由 WebView 决定，Crystal 的编译期优势用不上；CrystKit 已占此位 |
| 原生控件 | Capy、GTK4.cr | **不采纳** | 上限由 toolkit 决定，无差异化；GTK4.cr 已满足需求；跨平台一致性差 |
| 布局引擎 | Clay | **采纳为子系统** | 独立两遍布局 + 文本测量缓存是对的抽象，Crystal struct 很适合 |
| 嵌入式对象树 | LVGL | **不采纳** | 目标平台不符；但其“无效区域 + 部分刷新”思路可用于脏矩形优化 |

**结论：以路线 2 为骨架，吸收路线 1 的事件驱动与后端抽象、路线 5 的布局内核、路线 6 的脏矩形。**

## 3. 定案：为什么是自绘而不是绑定

1. **绑定路线没有空位**：GTK4.cr（原生控件）、CrystKit（WebView）、crystal-imgui（工具 UI）已各据一方。再做绑定是重复劳动。
2. **自绘路线在 Crystal 完全空缺**：没有 Gio/DVUI/Fyne 级实现。CrymbleUI 方向接近但不支持 macOS，且非 retained 全平台方案。
3. **语言特性只有自绘才用得上**：宏 DSL、编译期分派、struct 热路径、单二进制，这些优势在绑定 C toolkit 时都被 C 侧吸收掉了。
4. **Execution Contexts 移除了历史阻碍**：过去“Crystal 做 GUI 必须让出主线程”的论述在 Isolated context 出现后失效，自绘主循环现在是语言明确支持的场景。

## 4. 总体架构

### 4.1 分层

```text
┌─────────────────────────────────────────────────────┐
│ 应用层：声明式 DSL（宏展开）+ 响应式状态 Signal        │
├─────────────────────────────────────────────────────┤
│ Widget 层：Button/Text/Input/Scroll/List（虚拟化）     │
├─────────────────────────────────────────────────────┤
│ 核心层                                                │
│  ├─ Retained 树 + 失效传播（layout / paint / layout）  │
│  ├─ 布局内核：两遍、纯函数、文本测量缓存（Clay 式）     │
│  ├─ 绘制命令流 DrawList + 脏矩形                      │
│  └─ 事件路由：命中测试、焦点、IME、无障碍树             │
├─────────────────────────────────────────────────────┤
│ 渲染后端：Metal / Vulkan / OpenGL 回退                 │
│  ├─ 字形 atlas + 批处理                               │
│  └─ 路径：stencil/cover（Gio 式），M3 之后             │
├─────────────────────────────────────────────────────┤
│ 平台层：窗口、输入、剪贴板、IME、DPI、文件对话框         │
├─────────────────────────────────────────────────────┤
│ 文本栈：HarfBuzz shaping + FreeType 栅格化（FFI）      │
└─────────────────────────────────────────────────────┘
```

### 4.2 线程模型（本方案的核心）

```text
Process
├─ UI context        = Fiber::ExecutionContext::Isolated.new("ui")
│   └─ 独占主线程：平台事件循环、布局、绘制、所有 GPU/window C 调用
│      阻塞系统调用只影响本线程，不拖累其他 fiber
├─ Default context   = 默认（parallelism 1，可按需 resize）
│   └─ 业务逻辑、网络、I/O、响应式状态计算
└─ Worker context    = Parallel.new("workers", maximum: n)
    └─ 图片解码、大文本 shaping 预计算、数据加载

通信：一律 Channel / Sync；UI 只接收不可变快照，不共享可变对象。
约束：任何触及窗口/GL/Metal 的代码必须在 UI context 内编译期可识别地收敛，
      禁止业务代码直接持有后端句柄。
```

这样设计的三条理由：

- **正确性**：macOS 要求 UI 在主线程，GL context 有线程亲和。Isolated 提供语言级保证，不靠约定。
- **响应性**：业务侧慢 fiber 不会卡住绘制；UI 侧的阻塞 syscall 不会卡住业务。
- **可演进**：默认 context 日后 resize 即可多核，UI 侧不受影响。

### 4.3 帧流程

```text
平台事件 → UI context
  1. 输入分发（命中测试 → 焦点 → 处理器）
  2. 状态变更 → 标记失效（Layout / Paint）
  3. 布局内核：仅对 Layout 脏子树做两遍布局（约束下行、尺寸上行）
  4. 绘制：仅对 Paint 脏子树生成 DrawList，产出脏矩形集合
  5. 后端：atlas 更新 → 批次构建 → 提交（仅脏区域）
  6. 无事件则睡眠等待（Gio/DVUI 式事件驱动，不空转）
稳态要求：步骤 3–5 在内容未变时完全不执行。
```

## 5. 关键机制设计

### 5.1 布局内核（独立、可测、纯函数）

- 两遍：约束向下、尺寸向上；输出 `Rect` 数组。
- 输入输出全部为 struct；`Size`、`Constraints`、`Rect`、`Insets` 栈分配。
- 文本测量带缓存，键为 `(font_id, size, text_hash, max_width)`。
- **不依赖 widget 树**：内核只接收节点描述数组，可脱离 UI 跑单元测试与 fuzz。这是从 Clay 学到的最重要的一点——布局是可以独立做到微秒级且可验证的。

### 5.2 失效与重绘

- 三级失效：`Layout`、`Paint`、`CompositeOnly`（纯位移/透明度，滚动走这里）。
- 每个 widget 持有自身绘制缓存（离屏纹理），滚动时平移缓存而非重绘。
- 脏矩形合并后交给后端做部分提交；全屏变化才整帧重画。

### 5.3 响应式状态

- `Signal(T)` 拉取式依赖收集：读取即订阅，写时标记订阅者失效。
- 状态计算在 Default context；UI 侧只取结果快照，避免在绘制路径里跑用户代码。
- 大列表必须走虚拟化容器（视口内实例化 + 缓存位移），不提供“一次性建十万节点”的用法。

### 5.4 绘制与后端

- DrawList 为顶点/索引缓冲 + 命令批次，字形 atlas 共享，减少纹理切换。
- 后端trait 以泛型实现，编译期选定，无虚分派。
- 顺序：先做矩形/文本/图片批处理（覆盖 80% 业务 UI），复杂矢量路径的 stencil/cover 放到 M3。
- 不追求一步到位做通用 GPU 路径渲染——那是 Gio 多年积累的部分，也是最容易拖死项目的部分。

### 5.5 文本与无障碍（最高风险，前置验证）

- shaping 用 HarfBuzz，栅格化用 FreeType，FFI 绑定，不自写。
- CJK 换行、Emoji、RTL、组合字符、IME 预编辑与候选窗位置，必须在 M2 出可运行样例。
- 无障碍树与 widget 树同步维护，macOS 走 NSAccessibility，其他平台后置。

## 6. Crystal 特性的具体用法

| 特性 | 用在哪里 | 收益 |
|---|---|---|
| `struct` | 几何、颜色、约束、事件、DrawList 顶点 | 布局与绘制热路径零堆分配，直接降低 GC 停等 |
| 宏 DSL | `column { text "..."; button("OK") { ... } }` 编译期展开 | 声明式表达力，无运行时解释/反射 |
| 泛型 + 静态分派 | 后端、布局算法、容器 | 热路径内联，等同 Rust 单态化 |
| union 类型 | 事件枚举、样式值、布局尺寸（Auto/Fixed/Fraction） | 非法状态不可表示，省去运行时分支 |
| 非移动 GC | 持有 C 侧指针、atlas 纹理句柄 | FFI 安全，无需 pin |
| Isolated context | UI 主循环 | 语言级主线程保证 |
| Channel | 平台事件与业务状态跨界传递 | 无共享可变状态 |
| 编译期资源内嵌 | 字体子集、图标、默认主题 | 单二进制分发 |

## 7. 反目标

明确不做，防止范围膨胀：

1. 不做 WebView 封装，不做 DOM/CSS 兼容。
2. 不做 GTK/Qt 绑定，不与 GTK4.cr 竞争。
3. 不做 immediate mode API 作为主接口（可提供调试面板用的附属 immediate 层）。
4. 不做 3D 场景图、不做游戏引擎。
5. 不在 M3 前承诺复杂矢量路径与着色器特效。
6. 不在文本与无障碍验证通过前宣称“可用于生产”。

## 8. 里程碑与验证

| 阶段 | 内容 | 通过条件 |
|---|---|---|
| M0 技术验证 | Isolated context 跑窗口主循环 + 最小 Metal/GL 提交；HarfBuzz/FreeType FFI 打通 | macOS 窗口显示中文与 Emoji；业务 fiber 阻塞时 UI 仍响应 |
| M1 核心 | 布局内核 + retained 树 + 失效传播 + DrawList + 矩形/文本批处理 | 布局内核独立单测通过；静态界面稳态零分配、零重绘 |
| M2 交互与文本 | 输入、焦点、IME、滚动、虚拟列表、无障碍树 | CJK/Emoji/RTL 样例通过；万行列表滚动不掉帧（以帧时间分布为准，非平均帧率） |
| M3 平台与渲染 | Linux/Windows 后端、路径 stencil/cover、DPI、主题 | 三平台同一样例视觉一致；脏矩形部分提交生效 |
| M4 交付 | DSL 定稿、打包、文档、示例应用 | 单二进制分发；一个真实工具类应用跑通 |

验证方法遵循调研文档第 7 节：帧时间分布、分配率、输入延迟、文本正确性，禁止用平均 FPS 作结论。

## 9. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| GC 停等无法达到帧预算 | 核心卖点失效 | M1 起把“稳态零分配”作为 CI 指标；必要时热路径改对象池/arena |
| 文本栈复杂度被低估 | 消费级 UI 不成立 | M0 即做 FFI 验证，不延后；不实现则缩小定位为工具 UI |
| GPU 路径渲染工作量过大 | 项目拖死 | 延后到 M3；先用批处理覆盖业务 UI |
| 宏/泛型导致编译时间过长 | 开发体验崩坏 | 控制 DSL 展开规模；核心层避免过度泛型化 |
| 无障碍投入不足 | 无法进入生产 | 与 widget 树同步设计，不事后补 |
| 单人/小团队维护 | 生态难起 | 优先做“工具类应用可用”的窄切口，不做全场景框架 |
